# Kognitika — программа долгосрочного развития

Ревизия: 2026-08-09. Базис: `origin/main` at `49168ca`.

Этот документ связывает технический backlog с нейрокогнитивным видением из
`docs/Исследование рынка когнитивных D2C-приложений.md`.

Цель — не переписать продукт одним прыжком, а выстроить последовательность
направлений, где каждое опирается на уже работающий фундамент.

## Как читать этот документ

Предыдущая ревизия описывала строго линейные фазы 0–6 с правилом «не начинать
поздние фазы до verified-закрытия Фазы 1». На практике это правило уже
нарушено: Rust-аналитика (бывшая Фаза 5) и когнитивная безопасность (бывшая
Фаза 2) продвинулись раньше, чем закрылись задачи вовлечения, а рядом выросли
три направления, которых в плане не было вовсе — privacy/local-first,
физиологические данные и investor-контур.

Поэтому структура изменена: вместо одной линейной очереди — параллельные
**треки** с явными зависимостями между ними. Линейность сохранена там, где она
реальна: внутри трека и на границах, где данные одного трека определяют модель
данных другого.

Статусы:

- `завершено` — реализовано и подтверждено тестами;
- `в работе` — код есть на `main`, направление не закрыто;
- `запланировано` — контракт описан, реализации нет;
- `research` — гипотеза, не продуктовое обязательство.

## Текущее состояние платформы

Проверяемый фундамент:

- 31 продуктовый модуль тренировок, стабильные контракты публичных маршрутов,
  knowledge base и глоссария тегов;
- event-driven ядро: логика в `use{Module}Engine`, коммуникация через
  split `EventBus` с валидацией схем payload;
- seeded determinism во всех генераторах, headless-тесты вместо DOM-прогонов;
- Brain ID-first identity, Prisma/PostgreSQL, Firebase удалён из runtime;
- PII-safe logging, privacy-контуры с отдельным тестовым покрытием;
- repository-first deploy flow с контролем drift между git и production;
- governance-гейты для production DDL: обычный деплой не имеет права на
  миграции, DDL доступен только из отдельного reviewed workflow.

Незакрытые P0:

- **#221** — аудит source of truth production-деплоя и границы технических
  данных;
- **#220** — защищённый schema-guarded ADMIN recovery workflow (код
  safeguards на `main`, issue не закрыт).

## Трек A — цикл вовлечения и обратной связи

Статус: **в работе**, близко к завершению. Issues #46–#50.

Это направление превращает разовые тесты в систему развития. Оно первично для
всего остального: без стабильных trajectory, trend curve и event contracts
любая новая модальность заставит переписывать модель данных.

| Задача | Issue | Состояние |
| :--- | :--- | :--- |
| Рекомендация следующего шага после завершения | #46 | завершено |
| Ежедневная траектория проверки навыков | #47 | код на `main`, issue открыт |
| Кривая когнитивных способностей | #48 | код на `main`, issue открыт |
| Конкретная похвала после теста | #49 | код на `main`, issue открыт |
| Аудит доставки обратной связи | #50 | завершено |

Реализованные поверхности: `src/lib/daily-practice-types.ts`,
`src/server/services/daily-trajectory.ts`, `src/server/routes/daily-trajectory.ts`,
`src/lib/cognitive-trend-types.ts`, `src/lib/praise-engine.ts`,
`src/lib/practice-recommendations.ts` с тестами
`completion-recommendation-contract`, `daily-trajectory`, `cognitive-trend`,
`praise-engine`.

Заложенные решения, на которые опираются остальные треки:

- общий `DailyPracticeCategory` (`cognitive | somatic | safety`) вместо
  отдельной модели под каждый будущий вид практики — слоты для треков C и D
  уже существуют;
- кривая способностей строится как проекция над логом событий Brain ID, а не
  как денормализованная таблица. Это готовит Event Sourcing-подобную аналитику
  без переписывания;
- похвала привязана к измеримому изменению (скорость, точность, устойчивость
  внимания, улучшение к baseline, восстановление после ошибок), а не к
  общим формулировкам.

**Ближайшее действие:** сверить реализацию #47, #48, #49 с acceptance-критериями
и закрыть issues либо зафиксировать остаток. Расхождение между кодом и трекером
— главный источник неверных решений о приоритетах.

## Трек B — приватность и local-first

Статус: **запланировано**, высший приоритет после трека A. Issues #221, #222,
#224, #226.

Этого направления не было в исходном плане, и сейчас оно самое рискованное:
оно определяет, где вообще может находиться пользовательский профиль.

- **#221 (P0)** — аудит source of truth production-деплоя и границы
  технических данных. Пока он не закрыт, любые заявления о data boundary
  непроверяемы.
- **#222 (P1)** — practice-flow telemetry по умолчанию default-deny и без
  локальной передачи.
- **#226 (P1)** — local-only режим и зашифрованный IndexedDB identity vault.
- **#224 (P2)** — публикация verified data-processing inventory, retention
  policy и roadmap перехода к local-first.

Порядок здесь линейный и не подлежит перестановке: сначала аудит фактической
границы данных, затем default-deny телеметрии, затем локальное хранение
identity, и только потом публичные обязательства в документации. Обратный
порядок означает публикацию обещаний, которые нельзя подтвердить.

Зависимость: трек F (физиология) не может стартовать до закрытия #222 и #226.

## Трек C — когнитивная безопасность

Статус: **в работе**. Начат раньше, чем предполагал исходный план.

Уже на `main`: `src/core/cognitive-safety/index.ts`,
`docs/cognitive-safety-contract.md`, `src/tests/cognitive-safety-contract.test.ts`.
Существующие компоненты `SituationalJudgmentTest` и `DialogueArchitecture`
указывают в ту же сторону.

Практический путь — расширить диалоговые сценарии так, чтобы пользователь
учился распознавать паттерны манипуляции и выбирать здоровую реакцию.

Кандидаты паттернов: газлайтинг, ложная дихотомия, эмоциональное давление,
давление авторитетом, love bombing и изоляция, пропагандистский framing,
когнитивные shortcuts дезинформации.

Исследовательский отчёт указывает на prebunking/inoculation-подходы, игры типа
Bad News и Harmony Square, BITE model и conversational belief reframing.

Для кривой способностей (#48) здесь появляется второе измерение: не только
память, скорость и внимание, но и метрика `cognitive immunity`.

Acceptance horizon:

- typed contract `SafetyScenario` с labels для паттернов манипуляции;
- нейтральный, не алармистский русский copy;
- scoring, проверенный на синтетических сценариях;
- модуль остаётся образовательным, а не диагностическим.

## Трек D — мультисенсорное расширение и соматические практики

Статус: **запланировано**. Опирается на слот `DailyPracticeItem.category`
из трека A.

Отчёт говорит про визуальные, аудиальные, проприоцептивные, тактильные,
обонятельные и вкусовые каналы. Для web-платформы реалистичный порядок:

1. **Аудио** через Web Audio API: звуковая обратная связь на ответ,
   синхронизация с дыханием, опциональные ambient/focus modes, короткие
   attention reset cues. Нового железа не требует.
2. **Haptics** через Web Vibration API: вибропаттерн на верный и неверный
   ответ, mobile-only cues, pacing дыхательных упражнений, accessibility
   toggles.
3. **Соматико-созерцательный модуль**: slow-paced breathing около 0.1 Hz с
   визуальным таймером, короткие reset-практики между тестами, нейтральные
   attention practices без религиозного framing, расширенный созерцательный
   контент только по явному opt-in.
4. **Обоняние и вкус** — `research`, не продуктовое обязательство. Требует
   специализированного железа и отдельного hardware-партнёрства.

Правило продукта: без медицинских обещаний. Это инструменты восстановления,
внимания и устойчивости практики, пока отдельный legal/research review не
разрешит более сильный язык.

Acceptance horizon: typed contracts `SomaticPractice` и `BreathingPattern`,
доступный breathing timer с поддержкой reduced-motion, ясный safety/comfort
copy, интеграция в daily trajectory как optional и skip-safe item, хранение
только completion/progress events без чувствительных health data.

## Трек E — Rust как ядро аналитики

Статус: **в работе**, самый продвинутый из технических треков. Issues #139,
#140–#145, #167, #168, #223.

Rust — не стратегия переписывания. Это граница для вычислительно тяжёлых или
integrity-sensitive частей: агрегация длинной истории trend, антифрод-анализ
паттернов ответов, deterministic task generation, portable offline scoring.

Уже реализовано на `main`:

- `crates/kognitika-core` с parity-контрактом `AnalyzeSession` и собственными
  тестами;
- канонический контракт когнитивных событий и bridge от legacy `EventBus`;
- durable analytics outbox с воспроизводимыми job'ами и Node worker'ом;
- Rust shadow adapter, canary controls и preflight-проверки;
- runbook'и: `rust-analytics-canary-runbook.md`,
  `rust-postgresql-migration-authority.md`, `axum-analytics-sidecar.md`,
  `eventbus-rust-analytics-roadmap.md`.

Замеренная реальность, определяющая приоритет: TS ~0.098 ms/session против
Rust/WASM через Worker ~0.153 ms/session. **TS сейчас быстрее.** Поэтому
переключение на Rust-primary не обосновано производительностью и должно
оставаться за frame-budget-гейтом. Обоснование Rust лежит в детерминизме,
переносимости и integrity, а не в скорости.

Последовательность, которую нельзя сокращать: TS fallback → Rust parity →
shadow → canary → Rust-primary с сохранённым TS fallback.

Отдельно: **#223** — strangler-контракт для поэтапной миграции API на Axum.
Это направление шире аналитики и не должно стартовать до закрытия #221, потому
что затрагивает ту же границу технических данных.

Границы, зафиксированные исследованием: Rust для детерминированных
вычислительных ядер, но не для auth, не для UI и не для полного rewrite.
Analytics sidecar остаётся stateless, без DB-credentials и без публичного
ingress.

## Трек F — физиологические данные и wearables

Статус: **запланировано**, заблокировано треком B. Issues #148–#151.

- **#148 (P1)** — consent и privacy contract для физиологической обратной
  связи;
- **#149 (P1)** — версионированный контракт physiological session summary;
- **#151 (P1)** — shadow-политика для wearable-informed рекомендаций;
- **#150 (P2)** — Health Connect adapter с local-only summaries.

Частично начато: `src/core/wearable-consent/index.ts` и
`docs/wearable-consent-privacy-contract.md` на `main`.

Жёсткое условие: этот трек не стартует до закрытия #222 (default-deny
телеметрия) и #226 (локальный identity vault). Физиологические данные — самая
чувствительная категория в продукте, и вводить их до готовой local-first
границы означает создать проблему, которую потом придётся решать миграцией
пользовательских данных.

Рекомендации на основе wearable-сигналов должны сначала пройти shadow-режим,
как и Rust-аналитика: влиять на метрики, не влияя на пользователя, пока
качество не подтверждено.

## Трек G — научная валидация и партнёрства

Статус: **запланировано**, самый дальний горизонт.

Исследовательский отчёт опирается на 70+ источников. Это даёт Kognitika шанс
быть больше, чем ещё одним brain-training приложением, но только если модель
данных останется чистой.

Стратегические требования:

- только анонимизированные агрегаты;
- без raw Brain ID, email, token и private telemetry в exports;
- event log shape, пригодный для research review;
- явные consent boundaries;
- только синтетические fixtures в публичном коде и тестах;
- partner-facing документация отдельно от runtime code.

Зависимость: трек G бессмысленен без закрытого трека B. Научное партнёрство
требует проверяемых заявлений о данных, а не намерений.

## Принципы последовательности

Линейная очередь фаз заменена зависимостями между треками. Незыблемые:

```text
A (вовлечение)  -> C, D   контракты событий и trajectory первичны
B (приватность) -> F, G   граница данных до чувствительных данных
#221            -> #223   source of truth до миграции API
TS fallback     -> Rust-primary   только через shadow и canary
```

Правило, которое остаётся в силе: не расширять модель данных под новую
модальность до стабилизации trajectory, trend curves и event contracts. Если
добавить мультисенсорные или физиологические данные раньше, модель придётся
переписывать.

Дисциплина процесса не меняется:

```text
issue -> branch -> tests -> PR -> CI -> deploy -> verified status
```

Прямые production patches запрещены, кроме документированного emergency
rollback. Production DDL — только через reviewed workflow с runbook-ID.

## Регламент ревизии

Главная обнаруженная проблема управления — расхождение между кодом и трекером:
#47, #48, #49, #220 имеют реализацию на `main`, но остаются открытыми, а
исходное правило очередности фаз перестало соответствовать фактическому ходу
работ. Это делает приоритизацию недостоверной.

Поэтому:

- этот документ ревизуется при закрытии любого трека и при появлении нового
  направления, которого в нём нет;
- issue закрывается в том же PR, что и реализация, либо в issue фиксируется
  конкретный остаток;
- заявление «фаза завершена» требует ссылки на прошедшие тесты, а не на
  наличие файлов.
